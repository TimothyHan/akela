# Akela 일상 사용 가이드

> [guide.md](../guide.md)(영어)의 한국어판입니다. 내용이 다를 경우 영어판이 기준입니다.

Akela는 설계부터 에이전트 주도입니다. `init`이 프로토콜 3종(`PROTOCOL.md`, `ONBOARD.md`, `CURATE.md`)을 생성하고, 에이전트가 그것을 따라 전체 사이클을 돌리며, 여러분은 판단만 제공합니다 — 각 결정 지점마다 검토용 표 하나와 예/아니오 하나. 사이클:

| 시점 | 행동 주체 | 프로토콜 |
|---|---|---|
| 매 작업 | 에이전트: 컴파일 → 슬라이스로 작업 → 증거 기록 | `PROTOCOL.md` |
| 초기 스코핑 · 새 페이지 등장 | 에이전트가 scope/tier 초안, 여러분이 승인 | `ONBOARD.md` |
| 작업 중 중대 발견 | 에이전트가 지금 검토할지 물어봄 | `PROTOCOL.md` → `CURATE.md` |
| 매주 / 스프린트마다 | 에이전트가 검토 초안, 여러분이 승인, 적용 + 검증 | `CURATE.md` |

시간 예산: 설정에 약 1시간, 이후 검토당 약 10분. 이 가이드는 각 단계를 다룹니다.

## 1 · 설정: 지식을 가리키고, 중요한 것에 태그 달기

```bash
npx akela init --knowledge wiki     # akela.json + LEARNINGS.md + 에이전트 프로토콜 3종 (PROTOCOL, ONBOARD, CURATE)
#   --knowledge <dir>  기존 마크다운 폴더 아무거나 — wiki/, docs/, kb/, notes/ — 무편집으로 색인
#   --domain <pack>    선택: 도메인 팩 이름 또는 JSON 경로 (domains/README.md 참고); 기본 "default"
#   RAG: init 플래그가 아님 — 설치 후 akela.json 한 줄로 추가 (아래 리트리버 참고)
npx akela index                     # 주소를 가진 모든 섹션 나열
```

기존 마크다운 폴더는 한 글자도 고치지 않고 연결됩니다(`untagged: "derive"` 모드). 다만 파생 섹션은 scope가 `all`이라 여러분이 스코핑하기 전까지 패킹되지 않습니다 — 의도된 동작입니다. Akela는 관련성을 절대 추측하지 않습니다. 섹션을 진짜 지식으로 만들려면 태그를 다세요:

```markdown
## Refund approval
<!-- akela: id=approval scope=refund,damaged tier=must -->
Rule: refund requested under $25 and order within 14 days → approve; ...
```

- **`scope`** — 이 섹션이 적용되는 활동들(전부면 `all`). 활동은 그 도메인의 작업 단위입니다: `refund`, `deploy`, `triage`… `akela.json`에 선언합니다.
- **`tier`** — `must`(플로어: 해당 scope에는 항상 패킹), `should`(scope 일치 시 패킹), `context`(배경 지식; 나머지 뒤에).

`# H1` 다음 줄의 파일 레벨 태그는 파일 전체의 기본값이 됩니다.

**태그를 손으로 다 달아야 하나요?** 스코핑은 Akela가 뭐라도 하려면 필수입니다 — 스코프 없는 위키는 색인은 되지만 아무것도 패킹하지 않습니다. 조용한 오추측이야말로 이 도구가 막으려는 실패이기 때문입니다. 하지만 "필수"가 "여러분이 직접 타이핑"은 아닙니다. 침습성이 낮은 순서로 세 가지:

1. **설정에서 스코핑, 파일 무편집:** `akela.json`에 `"compiler": { "scope": { "WIKI-refunds#approval": { "add": ["refund"] } } }` — 위키 파일은 그대로.
2. **파일에 태그** — 위키를 직접 소유하고 있고 스코핑이 콘텐츠 옆에 보이길 원할 때 최선.
3. **에이전트에게 초안 맡기기** — `init`이 정확히 이 용도의 프로토콜을 생성합니다. 에이전트에게 *"Follow `akela/ONBOARD.md`"*라고 하면 위키를 조사해 섹션별 scope/tier를 (설정 전용과 태그, 두 형태 모두로) 제안하고 검토용 표를 전달합니다. 여러분의 승인이 선택권을 소유자의 손에 남깁니다.

**태그 하나가 사주는 것:** 그 섹션은 네 가지 의미에서 진짜 지식이 됩니다 — 위키 전체 쏟아붓기 대신 관련 규칙만 담긴 작은 슬라이스로 적절한 작업에 도달하고, `must`는 모든 매니페스트에서 증명 가능한 전달 *보장*이 되고, 집계·반증·은퇴·승격이 가능한 증거 단위가 되며(태그 없는 텍스트는 아무것도 얻거나 잃을 수 없습니다), 낡음이 감이 아니라 측정치가 됩니다.

작게 시작하세요. 에이전트에게 실제로 필요한 페이지 10개에 태그를 달고, 나머지는 파생 상태로 두면 증거(`stats`)가 놓친 것을 알려 줍니다 — 그게 핵심입니다.

`akela.json`의 선택 항목:
- **프로파일**은 변형 지식을 라우팅합니다: `"profile": { "plan": [{ "task": "^PRO-", "value": "pro" }, ...] }` — `Profile: plan=pro`가 붙은 학습은 일치하는 작업에만 패킹됩니다.
- **리트리버**는 RAG를 연결합니다: `"compiler": { "retrievers": [{ "name": "updates", "cmd": "node retrieve.js" }] }` — 커맨드가 stdin으로 activity/task/profile을 받아 `[{ id, heading, text, supersedes? }]`를 반환합니다.

## 2 · 에이전트 프로토콜: 컴파일 → 작업 → 기록

Akela의 일상 조작자는 여러분이 아니라 에이전트입니다 — 루프는 에이전트가 매 작업마다 돌려야만 작동합니다. `akela init`이 전체 프로토콜을 `akela/PROTOCOL.md`에 생성하며, 연결은 에이전트 지시 파일(`CLAUDE.md` / `AGENTS.md`)의 한 줄입니다: **"Follow `akela/PROTOCOL.md` for every task."** 프로토콜이 규정하는 루프의 형태:

```bash
akela compile --activity <activity> --task <id>   # 작업 전 — 슬라이스가 에이전트의 유일한 지식 소스
# … 슬라이스만으로 작업 수행 …
akela log applied <source-id>                     # 의존한 규칙마다 한 번
akela log contradicted <source-id> --note "…"     # 결과가 반증한 규칙 — 원문 그대로 인용
akela log outcome --status DONE                   # 실행 종료 (또는 BLOCKED / NEEDS_CONTEXT)
```

생성된 `akela/PROTOCOL.md`가 유일한 기준 문서입니다 — 위 루프 외에도 환경의 판정(리뷰, CI, 반려)을 의존했던 특정 규칙에 귀속시키기, 학습 제안 전 `akela vet` 검증, 미스코핑 드리프트 인지(모든 `compile`이 어떤 scope도 차지하지 않은 섹션 수를 출력하고, 그것이 생기거나 늘면 에이전트가 온보딩 초안을 제안합니다), **중대 증거를 깔고 앉지 않고 에스컬레이션하기** — `must` 규칙 반박, 지식 부재로 인한 작업 차단, 한 슬라이스 안의 상충 규칙이 있으면 에이전트가 지금 큐레이션 검토를 돌릴지 물어봅니다 — 그리고 지식 파일 직접 편집 금지까지 담고 있습니다. 지시 파일에 사본을 붙여 넣지 말고 파일을 참조하세요. 그래야 프로토콜 갱신이 저장소를 통해 모든 에이전트에게 도달합니다.

실험에서 비싸게 배운 두 가지 경험칙:

- **채널을 명시적으로 지목하세요.** "입력은 정확히 이것들"이라고 들은 에이전트는 바로 옆의 피드백 파일도 무시합니다. 환경이 판정(리뷰 결과, CI 실패, 고객 반려)을 만든다면, 지시에 그것이 어디 있는지, 그리고 반려는 의존했던 특정 규칙에 대한 `contradicted`가 되어야 한다는 것까지 적어야 합니다.
- **인용을 요구하세요.** 문제의 원문을 그대로 인용한 반박은 기계적으로 검증할 수 있지만, 의역한 반박은 엉뚱한 규칙을 비난할 수 있습니다. 인용 없는 실험에서 은퇴의 약 1/3이 잘못 귀속된 비난이었습니다.

## 3 · 큐레이션 루틴: 수치를 읽고, 결정하고, 편집

매주 또는 스프린트마다 — 그리고 실무는 위임할 수 있습니다. `init`이 `akela/CURATE.md`를 생성하므로, 검토를 시작하는 것은 에이전트에게 *"Follow `akela/CURATE.md`"*라고 말하는 것입니다(Claude Code라면 그 문장을 감싼 한 줄짜리 스킬이나 슬래시 커맨드로 `/curate`가 됩니다). 에이전트가 stats를 돌리고, 반박 노트를 읽고, 검토용 표 하나를 전달합니다. 여러분이 승인하면 적용하고 검증합니다. 직접 돌리려면:

```bash
akela stats
```

`finding` 열이 추천 큐입니다. 각 소견의 의미와 대응:

| 소견 | 의미 | 대응 |
|---|---|---|
| `falsified` | 서로 다른 실행 2회 이상에서, *그리고* 최근에(그 소스를 건드린 최근 3회 중 2회) 반박됨 | 먼저 반박 노트를 읽으세요. 규칙이 정말 낡았다면: 위키를 고치세요(섹션 재작성, 또는 삭제 후 관련 학습 `retired` 처리). *워커들이* 틀렸다면 — 특히 규칙을 방금 갱신한 직후에 흔합니다 — 그대로 두세요. 재작성의 깨끗한 기록이 낡은 불신을 이깁니다 |
| `promotion candidate` | 3회 이상의 실행에서 3번 이상 적용, 반박 0 | 진짜 사실이라면: 태그에 `from=LRN-…`을 달아 위키 섹션으로 쓰고 학습 상태를 `promoted`로. 패킹된 덕에 무임승차한 모호한 헤지라면: 두거나 은퇴시키세요 — 이 기준은 사용을 측정하지 진실을 측정하지 않습니다 |
| `promotion candidate → wiki (retire X)` | 검색 노트가 계속 이기며 섹션 X를 대체한다고 선언 중 | 노트 내용을 위키에 쓰고 X를 은퇴시키세요. RAG가 정본으로 졸업하는 순간입니다 |
| `restates <section>` | 위키 섹션을 중복 서술하는 학습 | 학습을 은퇴시키거나 차이만 섹션에 병합 |
| `unscoped (derive-mode)` | 어떤 scope도 차지하지 않은 페이지(또는 새 섹션) — 패킹되지 않고 에이전트에게 보이지 않음 | 에이전트에게 필요하면 스코핑(태그 또는 `compiler.scope`), 에이전트 지식이 아니면 그대로. 새 페이지는 이렇게 표면화됩니다 — 페이지를 쓸 때 태그를 기억할 필요가 없습니다 |
| 휴면 (전달됐지만 적용 0) | 매번 패킹되지만 쓰인 적 없음 | scope를 좁히거나, tier를 낮추거나, 은퇴 — 모든 슬라이스에서 자리세를 내고 있습니다 |

편집이 반영되기 전에 검증하세요(에이전트가 자기 편집을 수용하기 전에 돌리게 해도 됩니다):

```bash
akela check
```

`check`는 잘못된 id, 끊어진 계보, 유효하지 않은 상태를 거부하면서도 — 정당한 종료 상태(은퇴한 패밀리, 매달린 오버라이드)는 통과시킵니다. 더 엄격한 검증기라면 잘못 막았을 것들입니다.

**태그가 시간이 지나며 관리되는 방식:** 페이지 편집에는 태그 작업이 필요 없습니다 — 태그는 섹션과 함께 이동하고, 재작성은 증거 버전 범위화가 자동 처리합니다. 파생 모드 루트의 **새 페이지**(또는 새 섹션)는 즉시 인지됩니다 — 모든 `compile`이 미스코핑 섹션 수를 한 줄로 출력하고, 워커 프로토콜이 그 수가 생기거나 늘면 온보딩 초안을 제안하라고 지시합니다 — 그리고 다음 `akela stats`에 `unscoped`로 표면화됩니다. 태그 모드(`refuse`) 루트에서는 태그 누락이 시끄러운 색인 오류가 됩니다. 모든 섹션이 에이전트용인 위키에 적합합니다. **RAG는 태그가 아예 필요 없습니다**: 검색 항목은 자동으로 `EXT-` id와 `context` tier를 받고, 리트리버가 선언하는 것은 결과가 무엇을 `supersedes`하는지뿐입니다. 스코핑 백로그가 쌓이면 온보딩 초안을 다시 돌리세요: *"`akela stats`의 unscoped 섹션들에 대해 `akela/ONBOARD.md`를 따라 줘."*

**은퇴 메커니즘:** 학습은 `LEARNINGS.md`에서 `Status: retired`로 바꾸는 것으로 은퇴합니다 — 텍스트는 남고, vet 게이트가 그것을 툼스톤으로 사용합니다(그 수치나 표현을 재활용하는 새 캡처는 자동 거부). 위키 섹션은 페이지에서 제거하는 것으로 은퇴합니다. Akela는 이력을 `absent`로 표시하고 그 섹션이 얻었던 모든 이벤트를 추가 전용 로그에 보존합니다.

**규칙을 다시 쓸 때**(임계값 변경, 정책 갱신): 그냥 섹션을 편집하세요. 증거는 버전 범위화되어 있습니다 — 재작성은 깨끗한 기록으로 시작하고, 옛 텍스트가 얻은 비난은 `prior_versions`로 따로 보관됩니다. 복제 실험에서 나온 주의 하나: 여러분의 수정 *이전에* 헤매던 에이전트가 수정 *이후에* 그것을 진심으로 불신할 수 있습니다. 방금 재작성한 규칙에 `falsified`가 뜨면 행동하기 전에 노트를 읽으세요 — 수치는 정직하지만, 정직이 진실은 아니며, 신선한 수정은 무죄 추정을 받을 자격이 있습니다.

## 4 · 무엇을 기대할 수 있나

저희 측정(Sonnet급 에이전트, 60작업 실행) 기준: 컴파일된 슬라이스는 지식 베이스 크기와 무관하게 작업 관련 규칙 수에 비례하고(테스트 베드에서 ~100–200토큰), 정확도는 전부 쏟아붓기와 대등하며(~0.1 이내), 얻는 것은 *증명 가능하게* 최신인 지식 베이스입니다 — 낡은 규칙이 어텐션으로 가려지는 대신 측정 가능하게 컨텍스트 밖으로 나가고, 정답당 비용이 낮아지고, 사람이 실제로 읽을 수 있는 슬라이스가 남습니다. 루프의 알려진 한계는 3회 중 3회 재현됐습니다: 나쁜 규칙에 대한 올바른 불신과 좋은 규칙에 대한 잘못된 불신을 루프는 구별할 수 없습니다. 그 판단이 큐레이터의 일이고 — 당분간은, 여러분의 일입니다.
